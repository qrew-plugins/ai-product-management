# Interview rules

Used by `pm-ground` and `pm-scope`. The aim is shared understanding, reached in the other person's words, with every gap made visible.

## Pace
- Ask one question per message. Wait for the answer.
- Attach a suggested answer to each question, built only from the user's own words, their shared material (cite the source ID or decision ID) and the pinned banks. If none of those supports an answer, ask the question open, without a suggestion; never fill the gap with a plausible guess. Where a few options are likely, list them. The user can accept, correct or replace it.
- Keep questions short and plain. No acronyms the user hasn't used.
- Expect long, dictated answers. Pull out what matters and confirm anything that could be read two ways.
- Every 8 to 10 questions, post a one-line status (settled / still open) and carry on. When a 30-minute progress check-in is due (`PHASE-BRIEFING.md`), it replaces this line. Don't offer to wrap up; if the person asks, follow "When someone wants to go shorter".

## Words
- Use the user's names for tasks, roles, tools, records and documents exactly. Don't tidy, shorten or rename them.
- When a new term is needed, say that you are proposing one, define it in one sentence, give an example from the conversation, and ask whether to adopt it or use their word instead. Log the outcome in `CONTEXT.md`.
- Challenge thin reasoning, not vocabulary.

## Facts
- Facts come from the user, the banks, and material the user shared. Nothing else.
- "I don't know" is a valid answer. Ask around it once, then record it as an open question.
- When an estimate comes up, ask what it is based on.
- When an answer contradicts a bank (for example, the grounding document or an SOP), stop and point it out. Don't silently pick one; ask which is current and note the outcome.
- If a question can be answered by reading a file the user already shared (including anything in `apm/sources/`), read it instead of asking, and cite it.

## Finishing
- Say when there is enough to be useful, and stop asking.
- Produce the agreed output in the user's terms.
- List what is still unresolved as open questions, not as filled-in guesses.
- Ask what is wrong with the draft. Plan for at least one revision.
- Asked to ask fewer questions or to wrap up early: pause and follow "When someone wants to go shorter" in `../../../PHASE-BRIEFING.md`. Push back once, give the three choices, respect the answer, and record whatever is skipped as open questions. Short answers and "I don't know" are not shortcuts; accept them and keep going.
